# Участие в разработке руководства

Изменения проходят через ветку, локальные проверки и Pull Request в `main`.
Правки исходного приложения выполняются отдельно от этого учебного репозитория.

## Предложение изменения

Опишите проблему, аудиторию, правило и пример в Issue или в начале PR.
Для нового правила укажите идентификатор, уровень обязательности, причину,
пример применения и способ проверки. Не добавляйте правило только ради оформления.

## Локальная сборка

Нужен Python 3.12. Выполните в корне репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/check.py
python -m mkdocs serve
```

В PowerShell активируйте окружение командой `.venv\Scripts\Activate.ps1`.
Команда `check.py` запускает линтеры, строгую сборку и проверку внутренних HTML-ссылок.
Для отдельной сборки выполните `python -m mkdocs build --strict`.

## Ветка и коммиты

Создайте ветку от актуального `main`:

```bash
git switch main
git pull --ff-only
git switch -c codex/section-name
```

Используйте Conventional Commits: `type(scope): description`.
Тип `docs` — текст и структура руководства, `fix` — исправление проверки,
`ci` — workflow, `chore` — зависимости. Scope можно опустить.
Примеры: `docs: add accessibility rules`, `ci: validate and publish documentation`.
Один коммит должен описывать одно связное изменение.

```bash
git add docs/rules/new-section.md mkdocs.yml
git commit -m "docs: add new section"
git push -u origin codex/section-name
```

## Добавление раздела

1. Создайте `.md` в `docs/rules/`, имя файла — латинскими строчными буквами с дефисом.
2. Добавьте один H1 и правила с уникальными идентификаторами.
3. В `mkdocs.yml` добавьте путь в `nav`.
4. При необходимости обновите шаблоны и примеры.
5. Запустите `python scripts/check.py` и просмотрите страницу локально.
6. Откройте PR в `main` и приложите результат проверок.

## Ревью

Автор объясняет проблему, изменение и способ проверки. Рецензент проверяет
достоверность, понятность, соответствие глоссарию, доступность и ссылки.
Замечание должно указывать конкретный фрагмент, причину и предлагаемый результат.

В учебном обмене оставьте минимум три содержательных комментария к PR партнёра.
Автор исправляет замечания отдельным коммитом, отвечает в обсуждении и запрашивает
повторное ревью. После одобрения и успешных проверок выполните merge в `main`.
Если есть несколько авторов, одобрение должен дать другой участник.
Самостоятельная редактура не считается обменом ревью.

## Публикация

В настройках GitHub Pages выберите источник **GitHub Actions**.
Workflow `docs.yml` проверяет PR, но публикует сайт только после успешной проверки
ветки `main`. Результат публикации подтвердите успешным заданием `deploy` и
наличием нового раздела на сайте. Доступные в интерфейсе настройки могут зависеть
от прав и тарифа GitHub.
